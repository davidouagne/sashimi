# Represent column-level SQL facts as BackboneElement children, not extensions

**Status:** accepted, implemented (see [wayfinder map #18](https://github.com/davidouagne/sashimi/issues/18))

Until now, `StructureDefinitionMapper` expressed four SQL-column facts (Primary Key membership, Foreign Key target column, Unique Key membership, numeric precision/scale) as FHIR extensions on the column's `ElementDefinition`. Per an internal modeling standard, extensions are considered second-class for a Logical Model, so we decided to replace all four with nested `BackboneElement` children instead (e.g. `id.isPrimaryKey: boolean` instead of an `ext-sql-is-pk` extension).

We picked this over two alternatives: keeping the extensions as-is (rejected — doesn't meet the modeling standard), and dropping the native `Reference(...)` FHIR type on Foreign Key columns in favor of a fully descriptive/string-based representation (rejected — loses FHIR-native reference semantics and target-profile pinning for no benefit; instead, FK columns become a `BackboneElement` wrapper with the `Reference` typing preserved one level down, on a `.fkN.reference` child).

## Consequences

- **Schema fact → per-instance data field.** An extension on an ElementDefinition is metadata about the *schema*, declared once, at zero cost per data record. A `BackboneElement` child is a genuine data field: any real FHIR resource instance conforming to one of these Logical Models must now literally carry `isPrimaryKey: true`, `uniqueKeyName: "uq-code"`, `precision: 10`, or `targetColumn: "id"` in its own JSON, on every single row — even though the value is invariant across all rows for a given column. This is accepted as a cost of the chosen destination, not a defect to fix.
- **Breaking, all at once.** Every column that carries any of these four facts changes shape; there is no compatibility flag or transition period. All six golden fixtures are regenerated together when this is implemented.
- **`^maxLength` (and the column's own comment-derived `short` text) has no home on a Foreign Key column.** Today it's emitted even on `Reference`-typed elements, which is already semantically questionable (`maxLength` constrains string content; `Reference` isn't a string). Under the new model these move to a `.value` child — which Foreign Key columns don't have (see below) — so they are simply dropped there. Net effect: this migration incidentally removes a pre-existing, arguably-incorrect emission, not just adds new structure.
- **Foreign Key columns get no `.value` child.** A `Reference`-typed element already fully replaces the column's raw scalar typing today (`buildElement()` picks `Reference(Target)` over the primitive SQL type whenever the column has ≥1 FK, regardless of other facts). The new `.fkN.reference` child(ren) continue to play that role, so a separate raw-value child would be redundant. A column that is both Primary Key and Foreign Key therefore has `.isPrimaryKey` and `.fkN.*` as siblings, with no `.value`.
